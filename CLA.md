## 7. Acceptance procedure and records

This section defines the project's contributor acceptance process. A PR checkbox by itself is **not** sufficient.

### A. Individual-owned contributions

1. Read this Agreement, version **1.0**.
2. Open a pull request containing your Contribution.
3. Post the following exact statement **as a GitHub comment on that pull request, from your own account**:

   > I have read and agree to the CIWorkbench Contributor License Agreement version 1.0. I own the rights to my contribution, or have explicit permission from its rights holder to grant the rights described in this agreement. I grant Casper Rubæk the copyright and patent licenses set out in that agreement for my contribution to this pull request.

4. If there are multiple authors or co-authors, **each relevant rights holder** must accept or be covered by documented authorization. Do not post confidential employer documents in a public pull request.

### B. Employer- or organization-owned contributions

An authorized representative of the organization that owns the code must explicitly accept the Agreement on behalf of that organization and identify the contributors and scope covered.

The representative can post the following statement on the pull request from their own GitHub account:

> I am authorized to act for [legal name of organization]. On its behalf I accept the CIWorkbench Contributor License Agreement version 1.0 and grant the licenses described in it for the contributions by [GitHub usernames] to [PR number or scope].

Before merging, the maintainer must establish that the representative has authority. Where private documentation or separate corporate signatures are required, arrange that with the maintainer **before merging** and record only a non-confidential verification note on GitHub.

### C. Maintainer verification before merging

The maintainer must:

1. Review the pull request's authors and co-authors and ensure the necessary rights holders are covered by an individual or corporate acceptance.
2. Check that acceptance references **this Agreement version** and that any required employer authorization or third-party license provenance is documented.
3. Record a GitHub PR comment such as: `CLA verified — version 1.0; contributors covered: @username; acceptance: [comment URL]`. For company-owned contributions, note that separate authorization was checked without publishing private documents.
4. Merge only after verification. If authorization is uncertain, leave the pull request open and resolve it first.

The pull request, contributor acceptance comment and maintainer verification comment form the project's **auditable acceptance record**. Keep references to private supporting authorizations securely; do not commit them to the public repository.

This is a **manual process**, not an automated CLA-bot or an identity-verification service. The maintainer remains responsible for checking that the person granting rights has the authority to do so.
